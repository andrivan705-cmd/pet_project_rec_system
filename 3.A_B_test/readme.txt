 A/B-тестирование
1. Цель эксперимента
После разработки двух моделей рекомендаций (контрольной — из первого блока, и тестовой — из второго блока) необходимо объективно оценить, даёт ли новая модель статистически значимое улучшение пользовательского опыта. Основная проверяемая гипотеза:

H₀: Тестовая модель не превосходит контрольную по метрике HitRate@5.
H₁: Тестовая модель показывает более высокий HitRate@5.

Первичная метрика — HitRate@5 (доля пользователей, для которых хотя бы один лайкнутый пост попал в топ-5 рекомендаций).
Вторичные метрики — среднее число лайков на пользователя, CTR по рекомендациям и т.п. (будут рассчитаны на основе собранных логов).

2. Дизайн эксперимента
Для корректного сравнения моделей все пользователи были разделены на две равные группы (50/50) с помощью детерминированного хэш-функции:

Соль (salt): "my_salt" (вынесена в константу).

Алгоритм: MD5 от конкатенации user_id и соли; первые 8 символов хэша преобразуются в целое число, остаток от деления на 100 определяет группу:
percent < 50 → контрольная группа (control), иначе → тестовая (test).

Такое разбиение гарантирует, что один и тот же пользователь всегда попадает в одну и ту же группу при повторных запросах, что необходимо для воспроизводимости эксперимента. Размер выборки и длительность эксперимента определяются потоком реальных запросов к сервису.

3. Реализация A/B-сплитования в сервисе
3.1. Определение группы пользователя
В файле app.py реализована функция:

python
def get_user_group(user_id: int) -> str:
    value_str = f"{user_id}{SALT}"
    hash_hex = hashlib.md5(value_str.encode()).hexdigest()
    percent = int(hash_hex[:8], 16) % 100
    return "control" if percent < 50 else "test"
3.2. Загрузка двух моделей
При старте сервиса загружаются обе модели с помощью функции load_model(version):

python
model_control = load_model("control")
model_test = load_model("test")
Модели должны быть сохранены в файлы model_control.pkl и model_test.pkl в директории, указанной в переменной MODELS_DIR (или в текущей папке). Обе модели используют одинаковый набор признаков и возвращают вероятность лайка.

3.3. Логика эндпоинта /post/recommendations/
Получаем user_id и время запроса dt.

Определяем группу пользователя через get_user_group.

Выбираем соответствующую модель: model_control или model_test.

Подготавливаем признаки (аналогично предыдущим этапам) и делаем предсказания.

Отбираем топ-limit постов с наибольшей вероятностью лайка, исключая уже лайкнутые пользователем посты.

Формируем ответ в формате Response, который содержит:

exp_group — строка "control" или "test";

recommendations — список объектов PostGet с id, text и topic.

3.4. Логирование и сбор данных
Каждый ответ сервиса содержит информацию о группе пользователя. Это позволяет в дальнейшем по логам запросов и последующих взаимодействий (лайков, просмотров) собрать статистику для каждой группы и вычислить метрики.

4. Проведение эксперимента и анализ результатов
На данном этапе сервис уже готов к проведению A/B-теста. После того как система проработает некоторое время (например, несколько дней) и накопится достаточное количество данных (обычно не менее нескольких тысяч пользователей в каждой группе), можно переходить к статистическому анализу.

План анализа:

Собрать логи запросов к эндпоинту и последующих действий пользователей (лайки) за период эксперимента.

Для каждого пользователя вычислить индивидуальный HitRate@5 (1, если есть попадание лайка в топ-5, иначе 0).

Сравнить распределения HitRate@5 в контрольной и тестовой группах.

Применить двусторонний t-тест или непараметрический тест Манна-Уитни (в зависимости от распределения) для проверки статистической значимости различий.

Оценить размер эффекта (например, Cohen’s d) и практическую значимость.

На основе полученных p-value и размера эффекта принять решение о внедрении тестовой модели в продакшен.

5. Выводы и решения
На момент написания этого README эксперимент ещё не проведён, однако сервис полностью готов к его запуску. При условии, что тестовая модель (из DL-блока) обеспечивает HitRate@5 > 0.57 (что уже достигнуто), ожидается, что статистический тест подтвердит значимое превосходство над контрольной моделью.

В случае положительного результата тестовая модель будет объявлена победителем и станет основной для всех пользователей.

6. Что сделано лично мной
Разработка сплитования: реализовал детерминированное разбиение пользователей на группы на основе MD5-хэша с солью.

Интеграция двух моделей: переработал загрузку моделей так, чтобы сервис мог одновременно использовать контрольную и тестовую версии.

Модификация ответа сервиса: изменил схему ответа, добавив поле exp_group для логирования группы пользователя.

Подготовка к анализу: предусмотрел сбор всех необходимых данных (группа пользователя, выданные рекомендации) для последующего расчёта метрик и статистической проверки гипотез.

Автоматизация выбора модели: логика выбора модели в зависимости от группы пользователя полностью автоматизирована внутри эндпоинта.

7. Дальнейшие шаги
Запустить A/B-эксперимент на симулированных данных.

В случае успеха — переключить всех пользователей на тестовую модель и удалить код, связанный с A/B-разбиением (или оставить его для будущих экспериментов).
